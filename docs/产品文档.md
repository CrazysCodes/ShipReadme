# ShipReadme 产品文档

## 1. 产品概述

**ShipReadme** 是一个开源、自部署的 README 诊断与修复工具。

它面向开源项目作者、独立开发者和 side project 维护者。用户输入一个 GitHub 仓库地址后，ShipReadme 会读取公开仓库的结构和关键文件，分析 README 是否可信、完整、可运行，并基于真实代码事实生成改进建议和一版可复制的 README.md。

ShipReadme 的目标不是做一个大型文档平台，而是做一个小而精准的开发者工具：帮助项目在发布前拥有一份别人能看懂、能运行、愿意信任的 README。

当前产品状态：**MVP 版本已完成**。本文档用于沉淀当前产品定位、已实现能力、诊断原则和后续演进方向。

## 2. 产品定位

一句话定位：

> A README readiness checker for open-source projects.

中文解释：

> 一个面向开源项目的 README 发布前体检工具，基于真实仓库文件发现文档缺口，并生成可直接使用的改进版 README。

## 3. 目标用户

- 开源项目作者
- 独立开发者
- Hackathon / side project 作者
- 公司内部工具维护者
- 准备发布 GitHub 仓库的开发者
- 想提升项目可信度和上手体验的维护者

## 4. 核心痛点

很多项目代码本身不错，但 README 质量不足，导致：

- 访问者不知道项目解决什么问题
- 本地启动步骤不完整
- README 里的命令和真实项目脚本不一致
- 环境变量没有说明
- 有 Dockerfile 但没有部署说明
- 有测试脚本但没有贡献者运行测试指南
- 有 LICENSE 但 README 没说明开源协议
- 有截图或 demo 资源但 README 没展示
- 项目看起来“不可信”或“不成熟”
- 用户不敢安装，贡献者不敢参与

ShipReadme 的价值不是泛泛地“帮你写一篇 README”，而是：

> 根据真实仓库结构，指出 README 哪里缺、哪里不可信、哪里和项目实际不一致，并生成一份更可信、更完整、更可运行的 README。

## 5. MVP 范围

### 5.1 MVP 核心交互

用户打开 Web 页面后：

1. 输入 GitHub 仓库 URL
2. 点击 `Analyze repo`
3. ShipReadme 拉取公开仓库关键文件
4. 识别项目技术栈、脚本、配置、部署和文档信号
5. 输出 README 健康报告
6. 给出证据驱动的修复建议
7. 生成改进版 README Markdown
8. 用户复制 Markdown 或导出 patch

### 5.2 MVP 必须支持

- 输入公开 GitHub 仓库 URL
- 解析 GitHub URL 中的 owner / repo
- 调用 GitHub REST API 获取公开仓库内容
- 读取关键文件信号：
  - `README.md`
  - `package.json`
  - `pyproject.toml`
  - `requirements.txt`
  - `Cargo.toml`
  - `go.mod`
  - `Dockerfile`
  - `docker-compose.yml`
  - `.env.example`
  - `LICENSE`
  - `.github/workflows/*`
  - `test/`
  - `tests/`
  - `public/`
  - `assets/`
  - `docs/`
- 分析 README 是否覆盖关键内容
- 生成 README 健康分数
- 每个问题都必须有 evidence
- 生成修复计划
- 生成改进版 README Markdown
- 支持复制 Markdown

### 5.3 MVP 不做

- 不做登录
- 不做 GitHub OAuth
- 不做自动创建 PR
- 不做私有仓库分析
- 不做团队协作
- 不做项目管理
- 不做复杂文档站生成
- 不做多仓库批量扫描
- 不做长期监控
- 不做强依赖 AI

## 6. 核心原则

### 6.1 基于真实仓库事实

ShipReadme 的建议必须来自真实文件信号，而不是凭空生成。

示例：

- 如果检测到 `package.json` 中存在 `dev`、`build`、`test` 脚本，但 README 没写启动步骤，则提示 Quick Start 缺失。
- 如果检测到 `Dockerfile`，但 README 没有 Docker 部署说明，则提示 Deployment 缺失。
- 如果检测到 `.env.example`，但 README 没有环境变量说明，则提示 Configuration 缺失。
- 如果检测到 `LICENSE`，但 README 没有 License 段落，则提示 License 说明缺失。

### 6.2 不编造不存在的命令

生成 README 时，不能虚构项目没有的脚本或部署方式。

如果没有检测到 `test` 脚本，就不能写 `npm test`。
如果没有 Dockerfile，就不能写 Docker 部署步骤。

### 6.3 小而精准

ShipReadme 第一版只做 README 发布前诊断与修复。

不要扩展成通用 AI 文档平台。

### 6.4 开源自部署友好

第一版应能在本地运行。

没有 OpenAI API Key 时，也应通过规则引擎和模板生成工作。

## 7. 核心指标体系

ShipReadme 的报告由一个总分和多个诊断分类构成。

### 7.1 总分

`README Readiness Score`

范围：`0 - 100`

含义：

衡量当前仓库 README 是否足够清楚、可信、可运行、适合开源发布。

### 7.2 诊断分类

1. **Quick Start**
   - 是否能让用户快速安装和运行项目
   - 是否覆盖真实启动命令
2. **Configuration**
   - 是否说明环境变量和配置项
   - 是否与 `.env.example` 等文件一致
3. **Testing**
   - 是否说明测试命令、lint 命令或质量检查方式
4. **Deployment**
   - 是否说明 Docker、部署、构建产物或运行方式
5. **License**
   - 是否说明开源协议
6. **Contributing**
   - 是否说明贡献者如何开发、测试和提交
7. **Screenshots / Demo**
   - 是否展示截图、demo、示例输出或使用场景

## 8. MVP 诊断规则

### 8.1 Quick Start Missing

定义：

- 项目存在可运行脚本或入口
- README 没有清楚说明安装和启动方式

示例 evidence：

> `package.json` exposes `dev`, `build`, and `test` scripts, but README only says “install dependencies”.

### 8.2 Configuration Weak

定义：

- 仓库存在 `.env.example` 或配置文件
- README 没有解释环境变量或配置项

示例 evidence：

> `.env.example` defines `API_URL`, `DATABASE_URL`, and `AUTH_SECRET`, but README has no configuration table.

### 8.3 Deployment Missing

定义：

- 仓库存在 `Dockerfile` / `docker-compose.yml` / 构建脚本
- README 没有部署说明

示例 evidence：

> `Dockerfile` exists at repo root, but README has no Docker section or container run example.

### 8.4 Testing Missing

定义：

- 项目存在测试脚本、测试目录或 CI
- README 没有说明如何运行测试

示例 evidence：

> `package.json` contains a `test` script and `.github/workflows/ci.yml` exists, but README does not mention tests.

### 8.5 License Missing In README

定义：

- 仓库存在 `LICENSE`
- README 没有 License 段落或开源协议说明

示例 evidence：

> `LICENSE` exists, but README has no License section.

### 8.6 Contributing Missing

定义：

- 项目适合开源协作
- README 没有贡献说明，且没有 `CONTRIBUTING.md`

示例 evidence：

> No `CONTRIBUTING.md` was found, and README does not explain local development for contributors.

### 8.7 Screenshots / Demo Missing

定义：

- 仓库中存在可能的截图或 demo 资源
- README 没有展示或引用

示例 evidence：

> `public/assets/app-preview.png` exists, but README never references it.

## 9. 核心页面

### 9.1 Repository Intake

目的：

让用户输入 GitHub 仓库地址，并理解 ShipReadme 会基于真实项目文件分析 README。

核心元素：

- 品牌：ShipReadme
- 主标题：Ship a README people can trust.
- 副标题：Paste a GitHub repo and ShipReadme reads the actual project structure before suggesting a better README.
- 输入框：GitHub repository URL
- 示例：`github.com/yourname/side-project`
- 主按钮：Analyze repo
- 说明：
  - No account required for public repos
  - Self-hosted mode can run against private code later
- 检查项：
  - Install & run
  - Configuration
  - Tests & quality
  - Release trust
- 右侧预览：
  - `package.json`
  - `Dockerfile`
  - `.env.example`
  - `LICENSE`

### 9.2 Scanning

目的：

展示仓库正在被读取和分析。

核心元素：

- 标题：Reading the repository before writing.
- 进度条
- 当前仓库：`github.com/maya-labs/shipreadme-demo`
- 扫描步骤：
  - Read package metadata
  - Detect commands and dependencies
  - Compare README against project facts
  - Draft missing sections
- 终端风格日志：
  - found package.json scripts: dev, build, test
  - found Dockerfile but README has no deploy section
  - found .env.example with 5 variables
  - missing screenshot or demo media reference
  - generating evidence-backed repair plan

### 9.3 README Health Report

目的：

展示 README 健康分数、问题证据和修复计划。

核心元素：

- 总分：74 / 100
- 评价：Readable, but not ready to ship.
- 问题分类：
  - Setup: Missing
  - Config: Weak
  - Deploy: Missing
  - Contributing: Good
- 问题列表：
  - 优先级
  - 问题标题
  - Evidence
  - 影响说明
- 修复计划：
  - Replace vague setup section
  - Add Docker quickstart
  - Document `.env.example`
  - Insert project preview image

目的：

核心元素：

  - README.md
  - Quick start
  - Configuration

  - 分数：94 / 100

## 10. 视觉方向

界面语言：英文。

整体风格：

- 克制
- 工程感
- 清爽
- 高级
- 专业可信
- 信息密度适中
- 不做营销落地页
- 不做大型 SaaS 风格
- 不做装饰性插画页面

视觉要求：

- 背景：off-white / light gray
- 主文字：深墨色
- 健康状态：绿色
- 警告状态：琥珀色
- 高风险问题：红色
- 字体：Inter 或系统 sans-serif
- 文件路径、终端日志、evidence：monospace
- 卡片：1px 边框
- 圆角：8-12px
- 阴影：克制或无阴影
- 不使用花哨渐变、漂浮装饰球、大型 hero 装饰

## 11. 技术方向

MVP 推荐技术栈：

- Next.js
- React
- TypeScript
- Tailwind CSS
- GitHub REST API
- Next.js Route Handler 或轻量 API
- 规则引擎 + 模板生成
- AI 可选，不作为 MVP 强依赖

核心架构原则：

仓库读取、文件信号提取、诊断规则、README 生成必须分层。

标准输入：

```ts
type RepositoryFile = {
  path: string;
  content?: string;
  type: "file" | "directory";
  size?: number;
};
```

标准仓库信号：

```ts
type RepositorySignals = {
  readme?: string;
  packageJson?: {
    scripts?: Record<string, string>;
    dependencies?: Record<string, string>;
    devDependencies?: Record<string, string>;
  };
  envExample?: string;
  dockerfile?: string;
  dockerCompose?: string;
  license?: string;
  hasTests: boolean;
  hasCI: boolean;
  screenshots: string[];
  docsFiles: string[];
};
```

标准输出：

```ts
type ReadmeReport = {
  score: number;
  categories: {
    quickStart: string;
    configuration: string;
    testing: string;
    deployment: string;
    license: string;
    contributing: string;
    demo: string;
  };
  issues: Issue[];
  repairPlan: RepairPlanItem[];
  generatedReadme: string;
};
```

推荐核心模块：

- `parseGitHubUrl(url)`
- `fetchRepositoryTree(owner, repo)`
- `fetchImportantFiles(owner, repo, tree)`
- `extractRepositorySignals(files)`
- `analyzeReadme(signals)`
- `generateReadme(signals, report)`

## 13. 成功标准

MVP 成功的判断：

- 用户能在 1 分钟内输入仓库并看到报告
- 用户能相信报告基于真实仓库文件
- 用户能看懂 README 当前缺什么
- 用户能复制一版可用的 README
- 用户愿意拿自己的真实仓库试一次
- 用户认为它比“直接问 AI 写 README”更可信
